# Qualia2FA

![Qualia2FA](docs/qualia2fa_logo.svg)

一个**无中心服务器、不实时同步**的多平台双因素认证（2FA）应用。

English version: [README.en.md](README.en.md).

不同设备各自独立运行，不依赖任何厂商的服务器，也不需要注册账号或设置主密码。
在已登录同一账号的设备之间可以直接分享 2FA 条目，合并规则取并集。

| 项 | 值 |
|---|---|
| 平台 | Windows 桌面（已实现）；Android、iOS 计划中 |
| 界面 | Compose Multiplatform |
| 界面语言 | 英文（默认）、中文 |
| 许可证 | Apache-2.0 |

## 设计取向

- **无中心**：没有服务端、没有账号体系、没有「忘记密码」流程。你的密钥只在你自己的
  设备上。
- **不实时同步**：设备之间按需手动分享，而不是后台持续对账。因此不存在「同步冲突」
  这个类别的问题，也不会因为服务器宕机而拿不到验证码。
- **端到端加密**：条目在离开设备前就已加密，分享通道上的任何中间人都拿不到明文。
- **离线可用**：断网时所有功能照常，验证码照常计算。

## 当前状态

**开发早期，目前只有 Windows 桌面端。** 已经能用的部分：

- **界面**：进入程序先是加载界面（标志、名称、加载环；窗口变窄时环移到下方，变矮时先去
  掉名称、再去掉环），随后是没有密钥时的登录界面，或者主界面
- **主界面**：2FA、同步、设置三个界面共用一套导航，横屏时导航在左侧、竖屏时在底部，当前
  界面高亮；每个界面都按窗口尺寸调整布局
- **首次运行**：创建保险库（设备身份交给平台密钥库；主密钥由平台密钥库中一把**不可导出**的
  密钥包裹，落盘的是**包裹后**的形式；拿到的是 TPM、Android Keystore 还是软件库都如实报告），
  或者从另一台已解锁的设备配对登录。已经持有主密钥的设备只会看到「解锁」与
  「登录」，不会被引导去创建新保险库——那会顶掉它手里的密钥。保险库**打不开**时（密钥读不
  出来，或者文件已丢），那个界面上还有一个重置入口：它会先讲清楚删掉哪些东西，确认之后本机
  回到初次运行
- **条目**：手动增 / 改 / 删，从一张 `otpauth://` 二维码图片导入，或者直接粘入一条
  `otpauth://` 链接；进入多选后可以一次删除若干条（删除前会明确问一次，因为墓碑会同步到
  其它设备）。**五种条目**都能建：基于时间、基于计数器、mOTP、Yandex OTP、Steam
  Guard——后三种各自算出不同形状的验证码，编辑器里选哪一种就按哪一种算。mOTP 与 Yandex OTP
  需要一个 PIN，而它**只进不出**：界面只告诉你「已设置」，从不显示它。导入链接或二维码时按
  链接自己声明的类型带上
- **验证码**：实时显示、一键复制（30 秒后自动清空剪贴板，且只清掉自己写进去的那份）。
  基于时间的条目带倒计时环；基于计数器的条目显示验证码属于第几个计数器，并由「下一个验证码」
  推进它——服务器消费掉一个码，下一次就该用下一个。HMAC-SHA-1 / SHA-256 / SHA-512 三种算法
  都支持：条目的算法在编辑器里选，「+」菜单导入链接或二维码时按 `algorithm` 参数带上
  （链接里没写就是 SHA-1，这是 `otpauth://` 自己的默认值）。mOTP 出六位十六进制、Yandex
  OTP 出八个小写字母、Steam Guard 出五个字符——形状由各自的 scheme 定，因此编辑器对这三种
  不提供位数与周期
- **配对**：在同步界面里发起；配对码、请求与应答都走与同步码同一条码路径——一个二维码装不下
  的载荷会依次显示多张，读取时逐张收齐——文本始终留在码下面
- **同步**：两台设备各出示一个同步码、一次走一个方向；两边不一致的地方逐个交给用户裁决
- **同一 WiFi / 热点下**：配对请求与同步数据不必再由人搬运，两台设备互相发现之后，请求与
  应答自己沿局域网走过去。二维码仍然是配对的**带外锚点**——第一次配对仍然要扫一次码，
  它钉住「对方是哪台设备」，局域网只是省掉之后的人工搬运。局域网通道**按需打开**：需要
  它的界面才开、离开即关，不做后台同步，也不会在后台公告自己
- **设置**：界面语言、主密钥与设备身份**实际**的保护方式、恢复密钥导入导出、立即锁定
- **恢复密钥**：导出（口令要输两遍）与导入（先确认替换本机保险库，再输口令）
- **导入**：设置里的「从其它应用导入」读别的认证器导出的文件（JSON、HTML，或每行一条
  `otpauth://`；加密的 JSON 要口令）。**先看后写**：读出来先给你看它有哪些条目、哪些行用不了、
  哪些东西没能带过来，你确认之后才写进保险库。已经在库里且完全一致的条目直接跳过；用的是同一
  把密钥、但字段不同的条目**一定**会问你——替换、跳过、加入、还是两条都留，由你决定
- **导出**：设置里的「导出」把整份保险库写成别的认证器能读的四种格式之一——每行一条
  `otpauth://`、JSON、加密 JSON、HTML 表格。**只有加密 JSON 需要口令，也只有它是加密的**：
  另外三种是明文，界面在你选格式之前就会说清楚；HTML 那种还会给每个条目画一张二维码，方便
  用一部手机一条一条地搬过去。保存位置走系统自己的保存框。分组与组内排序只有两种 JSON
  带得走，另外两种会把条目落回顶分组——这一点同样写在选格式的地方
- **锁定**：打开 15 分钟后自动锁，也可以在设置里立即锁定；锁定时主密钥材料被释放、剪贴板
  被清空，回到登录界面可以解锁。**失焦不锁**：文件对话框会让窗口失焦，那样连二维码都选不完

还没有的：多账号、主密钥轮换、Android 与 iOS。

## 兼容性

**保险库格式版本 3，同步载荷版本 3。** 这个版本与 0.1.x **无法同步**：载荷只接受当前版本，
两端拿到的是一条明确的版本错误，而不是「认证失败」那种会把排查引向密钥问题的报错。因此两台
设备必须**一起升级**——0.1.x 会把 mOTP 条目读成一条普通 TOTP，PIN 与步长在一来一回里静默
消失，抬版本号要挡住的正是这件事。

版本 1 与版本 2 写下的保险库文件仍然打得开（可读版本只增不减）。

## 构建与运行

本仓库**不含任何 submodule**。Rust 各层都在自己的仓库里开发、发布到 crates.io，应用这一侧
按版本依赖它们：

| crate | 内容 | 许可证 |
|---|---|---|
| `qualia-dik` | 设备身份原语（表示 / 指纹 / 验签）与平台原生硬件密钥库；唯一允许 `unsafe` 的 crate | LGPL-3.0-or-later |
| `qualia2fa-core` | 全部密码学、保险库格式、同步与配对协议。无 I/O、无时钟、无 `unsafe` | LGPL-3.0-or-later |
| `qualia2fa-ffi` | 把核心库暴露为 UniFFI 绑定（Kotlin / Swift），并附带绑定生成器 | LGPL-3.0-or-later |
| `qualia-transport` | 传输通道：二维码这一半（容量模型、编码、渲染、文本信封、图像解码）与局域网这一半（组播发现、连接信息、QUIC 数据面）都已实现 | LGPL-3.0-or-later |

构建需要 JDK 21 与 Rust 工具链（Windows 上是 MSVC）：

```bash
git clone https://github.com/Qualia2FA/Qualia2FA
cd Qualia2FA

./gradlew :composeApp:jvmTest      # 编译 + 跑单元测试（含打通 Rust 库的往返测试）
./gradlew :composeApp:run          # 起桌面应用
./gradlew :composeApp:packageMsi   # 打包（jlink + jpackage）

./gradlew :composeApp:assembleRelease  # Android 安装包（签名、可直接安装）
./gradlew :composeApp:assembleDebug    # Android 调试包，只用来验证功能
```

要在设备上看这个应用是什么样，请用 `assembleRelease`：**Android 拒绝优化 debuggable 的
包**，debug 构建因此天生慢好几倍，拿它判断流畅度会得出与用户所见相反的结论。
`assembleRelease` 需要签名才能安装，签名信息从仓库根目录的 `keystore.properties`（不
提交）读；没有那个文件时回退到 debug 密钥，够本地安装，但不是可以对外发布的身份。

应用构建的是**已发布**的 `qualia2fa-ffi`：源码在配置阶段从 crates.io 取下来、按索引里的
SHA-256 校验后解包进 git 忽略的 `composeApp/rust/`。换版本时**必须同时换掉
`ffiCrateSha256`**：只改版本号会在校验那一步失败，这是故意的，它挡住了「版本号写着新、
实际拿到旧包」这类静默错配。

每次推送都会在 GitHub Actions 上跑一遍同样的构建：先跑单元测试，再构建 Windows 的 MSI
与 EXE 安装包，产物挂在那次运行的页面上。

要单独构建某一层，进它自己的仓库里做：

```bash
cargo test --all-targets        # Qualia2FA-Core
cargo test --all-targets        # QualiaDeviceIdentityKit（含打真 TPM 的集成测试）
cargo test                      # Qualia2FA-FFI
cargo test --all-targets        # QualiaTransport
```

## 目录结构

```
composeApp/
├── src/commonMain/             界面与业务代码（Kotlin，跨平台）
│   ├── composeResources/       标志与图标（drawable/），界面文案：values/ 英文（默认）、values-zh/ 中文
│   └── kotlin/dev/qualia/qualia2fa/
│       ├── Layout.kt           按窗口尺寸决定布局的规则，写成纯函数以便测试
│       ├── Theme.kt            取色、圆角与间距：色板来自标志本身（#EAF2F4 与 #091012）
│       └── *Screen.kt          加载、登录、2FA、同步、设置，以及配对的两侧
├── src/androidJvmMain/         桌面端与 Android 共用：保险库文件，以及写在它旁边的包裹后主密钥
├── src/jvmMain/                桌面端实现：数据目录、文件对话框、窗口
├── src/androidMain/            Android 实现：Activity、相机、文件选择器
└── src/jvmTest/                单元测试
```

`Qualia.kt` 是全仓唯一 import 生成绑定的文件：界面只看到普通的 Kotlin 值，绑定层要换、
要打补丁或 fork 时只动这一个文件。两处绝不能越过这条线的东西——条目列表与主密钥的存法
——也在那里包好。

主密钥本身从不落盘：平台密钥库内部生成一把密钥加密密钥，它不外泄，数据目录里存的是它
产出的密文。因此拷走那个文件并不等于拷走账号；设置界面会如实显示是哪个后端在保护它
（`tpm`、`android-keystore` 或 `software`）。

`icons/` 下是打包用的 `.ico`（Windows 安装包与窗口图标），由 `icons/make_ico.py` 从
标志重新生成。

## 界面语言

文案放在 `composeApp/src/commonMain/composeResources/`：`values/` 是默认语言（英文），
`values-zh/` 是中文翻译。默认跟随系统语言，登录界面与设置界面都能手动切换，选择记在数据
目录下的 `settings.properties` 里。

登录界面上那个切换器是**刻意**放的：那是保险库打开之前最后一个界面，读不懂界面语言的人
如果只能到设置里改，就等于改不了。

`StringsTest` 会比较两份文案的键集合：漏掉一条翻译在运行时只会静默回退到英文，只有这个
比较能发现它。

## 参与贡献

三条硬约束，动手之前请先看一眼：

- **密码学实现不接受「看起来能跑」的改动。** 一切以规范正文的测试向量为准。
  核心库已有 RFC 4226 / 6238 / 4648 / 9106 的向量测试，新增实现必须同样有出处。
- **秘密材料不得进入日志、错误消息或持久化的明文中。** 这是不可协商的。
- **不得静默降级。** 硬件密钥库不可用时必须如实上报，由用户决定是否接受较弱的
  保护，而不是悄悄换成软件密钥。

改界面文案时记得**两份都要改**（英文与中文），否则用户看到的是回退后的英文。
